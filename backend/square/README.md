# Square catalog sync V1

Status: implemented and qualified locally; real Square Sandbox catalog transport
passed. Production linking, deployment and scheduled sync remain off. See the
[checkpoint](../../docs/checkpoints/SQUARE_CATALOG_SYNC_20261110.md) for exact
proofs and remaining release gates.

V2 extends this catalog lane with opt-in automatic inclusion of eligible new
public For sale copies, exclusive one-unit physical stock, authenticated order
settlement and separate refund/confirmed-return handling. The existing grookai
QR is always generated by grookai. Connect once, choose a Square location, then
enable automatic inclusion and Square selling; subsequent eligible copies need
no manually created Square item. Private collection entry remains private.

The existing grookai /q/{GVVI} URL becomes the Square variation SKU. Connect once,
choose a location and explicitly select eligible public vendor copies. Optional
ongoing sync updates only that selection. Names never identify inventory.

- catalog_plan_v1.mjs: pure planner; unchanged URL, exact USD cents, complete
  same-scope snapshots, adoption/conflict checks and full-object updates.
- client_v1.mjs: fixed HTTPS origins, API2026-09-16, bounded IO, safe errors,
  OAuth exchange/refresh, verified merchant/location and exact-SKU catalog IO.
- credential_envelope_v1.mjs: authenticated, domain-bound private token storage.
- service_v1.mjs / backend_service_v1.mjs: owner-bound durable operations,
  one-use browser OAuth, fenced leases, refresh recovery, backoff and adoption.
- worker_v1.mjs / run_worker_v1.mjs: bounded environment-scoped ticks and durable
  health history. No scheduler is installed by importing or testing these files.
- qualify_sandbox_catalog_v1.mjs: explicit private prepare/apply proof using an
  existing Sandbox test-account token. No Supabase access or seller OAuth binding.

The thin API and Account connection manager are in apps/web. Database migrations
are local-only candidates and private authority is independently default-off.
User selection is requalified through existing ownership, entitlement, public
sharing, sale intent and verified printing rules. Fixture booleans do not grant
HTTP authorization.

New tracked catalog entries receive **no allocated quantity** from the catalog
lane itself. `commerce_service_v2.mjs` separately acquires a durable exclusive
claim, saves the exact idempotent stock request, then confirms stock1. It reconciles
authenticated completed/fully paid Square orders before checking stock, preventing
an observed sale decrement from replenishing the same copy. Ambiguity retains the
claim for review. Financial refunds never imply physical return or automatic stock.
Preserve existing taxes, modifiers, sibling variations, stock settings and full
object versions. A missing mapped target or edited provider field stops for
review; an unmapped same-SKU item requires explicit adoption.

fixture must never become an actual owner's inventory. Choose a new private

CSV contains new items only, with blank import Tokens. Reimporting it can create
duplicates; it is a preview/fallback, not recurring sync. Obtain the merchant's
current location columns/template before import. Do not import this fixture.

The real Sandbox proof requires a documented private SQUARE_SANDBOX_ACCESS_TOKEN,
SQUARE_APP_ID beginning sandbox-, and SQUARE_ENVIRONMENT=sandbox. Its output and
credentials must remain outside the repository in an operator-private directory.
It saves the exact request before writing, repeats only that saved request/key
and verifies one matching item. It refuses a fresh creation when a matching SKU
already exists. Prepare and review before apply:

```powershell
node --use-system-ca backend/square/qualify_sandbox_catalog_v1.mjs --prepare --env-file C:/PRIVATE/sandbox.private.env --out-dir C:/PRIVATE/new-proof
node --use-system-ca backend/square/qualify_sandbox_catalog_v1.mjs --apply --env-file C:/PRIVATE/sandbox.private.env --out-dir C:/PRIVATE/new-proof
```

The fixed transport fixture uses the previously owner-tested Aerodactyl QR at
USD20.00 and a clearly named Sandbox item. It is not production inventory, an
owner eligibility proof or complete OAuth testing. Never substitute a default
test token for the encrypted seller authorization-code flow. Do not rotate keys,
register a dead redirect or enable production controls to make a test pass.

`run_commerce_worker_v2.mjs --once --env-file <private-file>` is the bounded durable
recovery command; `--health` reads current run/claim/signal status. The hosted
post-save and verified webhook paths process immediately. The five-minute GitHub
workflow is an independent recovery path; cron can be delayed, so it is not the
immediate checkout path. Production credentials and seller OAuth are required;
the default Sandbox token must never stand in for seller authorization.

Local full HTTP qualification uses `scripts/schema/qualify_square_http_commerce_v2.mjs`
with real local Auth/SDK/HTTP/backend and a clearly separate loopback provider.
It tests private add, automatic item/stock, sale replay, refund and confirmed return.
Actual Square Sandbox commerce qualification is `qualify_sandbox_commerce_v2.mjs`.
Neither substitutes for the hosted/Samsung QR checkout acceptance.

Current release admission is `SquareCommerceReleaseV6`, exact483→493/ten pinned
migrations. Earlier catalog/baseline scopes remain unchanged. Run details retain
connection/owner/target, source version, last processing step and bounded database
error codes; they never retain raw provider bodies or secrets. Temporary lease
contention is pending work. A real catalog failure remains a failed run even if
the existing allocated quantity can still be read successfully.

Unsupported mapped orders record durable review and quarantine only their own
claims. Their saved uncertain stock bodies/keys remain retained, and those claims
cannot be automatically released or reallocated. Unrelated sales, new listings
and privacy withdrawals continue; reviewed orders do not monopolize the target
batch or leave webhook signals replaying forever. Provider outages and failed
review persistence retain their signals/cursor for retry. Reacquiring a released
copy requires a fresh zero count and uses the latest immutable allocation-request
clock, preserving earlier allocation and payment history.

The original payment creation clock must follow the physical allocation before
an authenticated paid order can dispose that copy. A historical payment/refund
is retained as evidence without consuming a later claim. Refund polling uses
its independent update feed before advancing the shared reconciliation cursor,
so a missed notification cannot depend on an old order changing. See Square's
[List payment refunds](https://developer.squareup.com/reference/square/refunds-api/list-payment-refunds).
`qualify_sandbox_reconciliation_v3.mjs` verifies this feed and normalization using
the existing Sandbox sale/refund with GET requests only.
