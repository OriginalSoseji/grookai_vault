## Current executable boundary

`stamped_child_image_intake_prepare_v1.mjs` is read-only. It validates canonical
project/verified TLS/maturity, the existing private `user-card-images` bucket,
every original image byte, every existing parent/child/active identity and a real
active founder entitlement. It captures relevant table definitions and rejects
existing candidate/evidence/event/raw/object collisions. It produces only an
unapproved private plan. It exposes no mutation operation. A successful plan is
not release qualification. The effective founder permission fingerprint binds
the entitlement ID, actual authenticated account, active status and founder role;
unrelated entitlement timestamps do not substitute for permission changes.

`backend/warehouse/run_stamped_child_image_intake_v1.mjs --config <private-file>`
is the separate guarded operator entry point. Writes default to disabled and
require `ENABLE_STAMPED_CHILD_IMAGE_INTAKE_V1=true`,
`STAMPED_CHILD_IMAGE_INTAKE_MODE=EXPLICIT` and the unchanged mechanical
`GROOKAI_PREFLIGHT_ACK=1` gate. They also require Windows/Node22.23.5, a clean
committed source matching the complete producer fingerprint, pinned genuine
normal commit/push/hosted qualification, and an exact separate owner decision.
Each of four frozen attempts has one exclusive output directory under
`C:/grookai_vault_operator_artifacts/stamped_child_image_intake_runs_v1/`.
An existing attempt directory stops execution. No automatic retry is allowed.
The `readback` mode is server-enforced read-only and grants no write authority.

## Proposed source intake

The separately qualified executor may propose at most 33 append-only raw
image objects and 33 rows each in `raw_imports`, `canon_warehouse_candidates`,
`canon_warehouse_candidate_evidence` and `canon_warehouse_candidate_events`.
Original bytes stay immutable. The raw receipt must reference the complete
preserved image payload and source provenance before warehouse processing.

The prepared shared-executor protocol has separate transactional SQL and
append-only Storage scopes. Storage permits no overwrite or cleanup; a partial
outcome is retained for independent diagnosis. The proposed four named attempts
are raw-object staging, database rollback, apply and zero-write replay. Each may
record at most one failure in `contract_violations` after its scoped decision is
validated. Invalid or missing production approval grants no failure-ledger write.
The frozen plan binds all four run IDs and stores the planned apply run and input
fingerprint in durable provenance. A lost commit response is uncertain until an
independent connection diagnoses it; no successful receipt may be fabricated.
The installed backend Supabase SDK supplies authentication and immutable uploads;
no hand-built JWT, Storage HTTP bypass or canonical image pointer is permitted.

Candidates must start as image-backed `MISSING_IMAGE`/`RAW` submissions. The
verified founder is the accountable submitter; the event explicitly identifies a
delegated `SYSTEM` source intake. This does not assert that the founder manually
uploaded, reviewed or approved the image. Do not fabricate a user, JWT, entitlement,
approval, identity-audit result or normalization event. No `SOURCE_BACKED` identity
shortcut from the unrelated discovery bridge is permitted.

Storage adapter, register their runtime scopes/proofs, pass ordinary local/source/
hosted checks, obtain a fresh exact plan and scoped owner decision, and prove the

existing canonical rows, reviews, identities, owners, mappings and prices stay
