The launch target is 100 vendors with 1,000 cards each, plus retained sold
history. The existing 1,000-target read can omit a sold mapping before the
application reserves its sold-recovery slot. A successful small batch does not
prove that every retained obligation is reachable.

The server-only `GROOKAI_SQUARE_RECOVERY_WINDOW_ENABLED` flag defaults off.
Only enabled, automatic, unfocused batches of exactly two or five targets send
`automaticRecoveryLimit` to the existing commerce authority. Manual, focused,
other-sized and default-off calls retain their original request and selection.

Both hosted clocks must carry the same server setting. The GitHub workflow
binds its repository variable with a false fallback; the scheduler adapter
serializes a missing setting as false into its private worker environment and
rejects malformed values before launching a worker. Cloud recovery passes the
same environment through `squareEnvironmentConfig`. This wiring does not
create or enable a repository/Vercel control. Actual-adapter and cloud tests
verify default-off behavior and explicit propagation to worker configuration.

Forward migration `20261123003000` adds a read branch inside the existing
service-only, owner-bound, leased and fenced `commerce_targets` action. It pins
the entire prior function definition and replacement marker, and rejects drift.
The connection lock and all service authentication execute before this branch.
No function owner, grants, search path, RLS policy or monetary writer changes.

The first branch could let a pending catalog request on one sold copy occupy
the live-work slot while another sold copy took the reserved slot. A later
actual-RPC counterexample reproduced two sold results and no active result.
Do not activate that first branch alone or rewrite its locally applied SQL.

Forward migration `20261123004000` pins that entire intermediate definition and
replaces only its automatic read branch. It separates live and sold lanes.
Live rows exclude sold allocations and retain pending-operation, copy-change
and transition priority. When sold history exists, live work may use at most
one less than the requested bound; the oldest sold rows by `updated_at,id`
fill the remainder. With only sold history, the full batch remains available.
The result keeps its seven original fields, has no duplicates and never
exceeds two or five. Pending requests on sold copies remain durably stored and
cannot consume the live lane. No sold copy is republished or given new stock.
